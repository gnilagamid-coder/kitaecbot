# Telegram Mini App — магазин-конструктор

Готовый магазин для Telegram, который разворачивается на своём VPS за 5 минут и
настраивается под любую нишу без правки кода: от классической корзины до витрины,
где покупка идёт только через личку менеджера.

- **Один магазин — без зависимостей.** Нужен только Node.js; ни базы, ни
  npm-пакетов. Данные — папка `data/`: несколько JSON и картинки. Бэкап —
  `tar czf backup.tgz data`, переезд — скопировать папку.
- **Платформа на много магазинов** — тот же код с `MULTITENANT=1`: клиенты
  регистрируются сами, каждый получает свой поддомен. Здесь нужен MySQL.
- **Бот в том же процессе.** По умолчанию long polling — вебхук и домен для
  самого бота настраивать не нужно.
- **Всё меняется из админки.** Тема, режим продаж, тексты, поля формы, уведомления.

> 🔰 **Ставите впервые?** Ниже пошаговый гайд с нуля: от заказа сервера до
> первого заказа в боте, с бесплатным доменом. Разбор частых ошибок — в конце
> раздела.

## Установка на Debian — пошагово с нуля

Гайд рассчитан на человека, который никогда не открывал терминал сервера. Всё,
что нужно печатать, дано целиком — копируйте и вставляйте. Весь путь занимает
20–30 минут, из которых сама установка ~5 минут, остальное — регистрации и
ожидание DNS.

### Что понадобится

| Что | Где взять | Сколько стоит |
|---|---|---|
| Аккаунт Telegram | уже есть | — |
| VPS с Debian 12 | любой хостинг | от ~200 ₽/мес |
| Домен | см. шаг 1 | от 0 ₽ |
| HTTPS-сертификат | Let's Encrypt, ставится сам | бесплатно |

Требования к VPS минимальные: **1 ядро, 1 ГБ RAM, 10 ГБ диска**. При заказе
выбирайте чистый **Debian 12** (или Ubuntu 24.04) — без панелей вроде ISPmanager,
они мешают.

> **Зачем вообще домен.** Сам бот работает и без него: он сам стучится к Telegram
> и отвечает на команды. Но **витрину внутри Telegram можно открыть только по
> `https://`** — обычный IP-адрес Telegram не примет. Домен нужен именно за этим.

---

### Шаг 1. Домен: бесплатный или платный

Оба варианта рабочие, разница в солидности и в том, чей это домен.

**Бесплатный — DuckDNS.** Даёт адрес вида `мойшоп.duckdns.org` за две минуты,
вход через Google или GitHub, регистрации нет. Поддомены работают тоже
(`клиент.мойшоп.duckdns.org` ведёт на тот же сервер) — это важно, если позже
захотите поднять платформу на несколько магазинов.

Минусы честно: домен не ваш, забрать его с собой нельзя, и клиенту вы даёте
ссылку с чужим именем в адресе. Для «попробовать» и для личного магазина —
отлично. Для продажи услуги клиентам — выглядит несерьёзно.

**Платный — свой домен.** В зоне `.ru` это ~200–400 ₽ в год, `.com` — ~1000–1500 ₽.
Регистраторы: reg.ru, timeweb, beget, nic.ru. Домен ваш, переносится между
хостингами, в адресе только ваше имя.

**Что выбрать.** Начните с DuckDNS — если магазин не пойдёт, вы ничего не
потеряли. Как только появятся первые клиенты, купите домен: перенос занимает
десять минут (поменять адрес в BotFather и перевыпустить сертификат).

#### Как получить бесплатный домен

1. Откройте [duckdns.org](https://www.duckdns.org), нажмите **Sign in with Google**.
2. Наверху страницы будет строка **token** — длинная строка вида
   `a7b1c9d2-3e4f-…`. Скопируйте в заметки, пригодится.
3. В поле **sub domain** впишите желаемое имя (например `mojshop`) и нажмите
   **add domain**.
4. IP впишем на шаге 4, когда сервер будет готов.

Ваш адрес: `mojshop.duckdns.org`.

#### Как настроить платный домен

После покупки в панели регистратора найдите раздел «DNS-записи» и добавьте
**A-запись**: имя `@` (или пусто), значение — IP вашего сервера с шага 2.
Если планируете платформу с поддоменами, добавьте вторую A-запись:
имя `*`, тот же IP.

### Шаг 2. Заказать VPS

Подойдёт любой провайдер: Timeweb, Beget, Selectel, RuVDS, Aeza, Hetzner.
При заказе: ОС **Debian 12**, самый дешёвый тариф, локация ближе к покупателям.

После оплаты хостинг покажет три строки — запишите их:

```
IP: 203.0.113.45
Пользователь: root
Пароль: xxxxxxxx
```

> **Про расположение сервера.** Если будете обслуживать чужих клиентов и хранить
> телефоны и адреса их покупателей — сервер должен стоять в России (242-ФЗ).
> Для личного магазина ограничений нет.

---

### Шаг 3. Подключиться к серверу

**Windows:** откройте «Пуск» → наберите `PowerShell` → запустите. **macOS/Linux:**
откройте «Терминал». Дальше одинаково — подставьте свой IP:

```bash
ssh root@203.0.113.45
```

При первом подключении спросит `Are you sure you want to continue connecting` —
напечатайте `yes` и нажмите Enter. Затем запросит пароль: **вводите вслепую**,
символы не отображаются, это нормально. Удобнее вставить правой кнопкой мыши.

Получилось, если строка сменилась на что-то вроде `root@vps12345:~#`. Теперь всё,
что вы печатаете, выполняется на сервере.

---

### Шаг 4. Направить домен на сервер

Вернитесь на duckdns.org, в поле **current ip** впишите IP сервера и нажмите
**update ip**. Затем проверьте прямо в SSH:

```bash
ping -c 3 mojshop.duckdns.org
```

В ответе должен быть **ваш** IP. Если другой или «Name or service not known» —
подождите 2–3 минуты и повторите: DNS обновляется не мгновенно.

> **Не идите дальше, пока здесь не появится правильный IP.** Сертификат
> выпускается проверкой домена, и на чужом IP он не выпустится.

---

### Шаг 5. Создать бота

1. Откройте в Telegram [@BotFather](https://t.me/BotFather), отправьте `/newbot`.
2. Введите имя бота — как он подписан в чатах, например `Мой магазин`.
3. Введите username — обязан заканчиваться на `bot`, например `mojshop_2026_bot`.
4. BotFather пришлёт токен вида `123456789:AAHdqTcvCH1…` — **скопируйте в заметки**.
5. Найдите своего бота по username и нажмите **Start**, отправьте `/start`.

> Шаг 5 обязателен: Telegram запрещает боту писать первым тому, кто с ним не
> общался. Пропустите — и уведомления о заказах просто не придут, без ошибки.

Токен — это полный доступ к боту. Никому не показывайте, в чаты не выкладывайте.
Засветили — `/revoke` в BotFather, получите новый.

---

### Шаг 6. Установить магазин

В окне SSH выполните три команды по очереди:

```bash
apt update && apt install -y git
```

```bash
git clone https://github.com/gnilagamid-coder/kitaecbot.git /root/tg-shop && cd /root/tg-shop
```

```bash
bash install.sh
```

Установщик задаст четыре вопроса:

| Вопрос | Что вводить |
|---|---|
| Токен бота от @BotFather | токен с шага 5 |
| Домен | `mojshop.duckdns.org` — **без** `https://` и без `/` в конце |
| Пароль в админку | нажмите **Enter** — сгенерируется надёжный |
| Внутренний порт | нажмите **Enter** |

Дальше он всё сделает сам: поставит Node.js 24, создаст системного пользователя,
настроит автозапуск, поднимет nginx и выпустит HTTPS-сертификат. Это 2–4 минуты,
по экрану будут бежать зелёные строки.

В конце появится рамка с адресами и паролем. **Сразу скопируйте пароль в
заметки** — второй раз он не показывается.

Проверьте: откройте в браузере `https://mojshop.duckdns.org/` — должна открыться
витрина с надписью «Каталог пока пуст», а в адресной строке замочек.

---

### Шаг 7. Подключить витрину к Telegram

Вернитесь в [@BotFather](https://t.me/BotFather).

1. `/newapp` → выберите своего бота.
2. **Title** — название приложения, например `Магазин`.
3. **Description** — короткое описание.
4. **Photo** — обложка 640×360; нет под рукой — отправьте `/empty`.
5. **GIF** — тоже `/empty`.
6. **Web App URL** — адрес витрины целиком, со слэшем: `https://mojshop.duckdns.org/`
7. **Short name** — короткое имя латиницей, например `shop`.

BotFather пришлёт ссылку вида `https://t.me/mojshop_2026_bot/shop` — скопируйте.

Затем `/setmenubutton` → выберите бота → вставьте ту же ссылку → введите надпись
на кнопке, например `Магазин`. Откройте чат с ботом: внизу появилась кнопка,
по нажатию открывается витрина прямо внутри Telegram.

И отдельно `/setdomain` → выберите бота → `mojshop.duckdns.org`. Без этого
web_app-кнопки внутри сообщений бота работать не будут.

---

### Шаг 8. Первый вход в админку

Админка открывается **прямо в боте**. Сначала разрешите себе вход:

1. Отправьте боту `/id` — он ответит вашим числовым `chat_id`.
2. На сервере впишите его в настройки и перезапустите:

```bash
nano /opt/tg-shop/.env
```

Найдите строку `ADMIN_CHAT_IDS=` и допишите свой номер (несколько владельцев —
через запятую). Сохранить: `Ctrl+O`, Enter, выйти: `Ctrl+X`. Затем:

```bash
systemctl restart tg-shop
```

3. Отправьте боту `/admin` → нажмите «⚙️ Открыть панель».

**Запасной вход**, если Telegram недоступен: откройте
`https://mojshop.duckdns.org/admin.html` и введите пароль из шага 6 в поле формы.
Токен намеренно не передаётся в адресе — query-параметры оседают в логах nginx
и в истории браузера.

---

### Шаг 9. Настроить и проверить

По вкладкам, сверху вниз:

1. **Уведомления** — добавьте свой `chat_id` и нажмите «Отправить тестовое
   уведомление». **Пока тест не прошёл, заказы до вас не дойдут.**
2. **Бренд** — название, эмодзи или логотип.
3. **Тема** — выберите пресет, цвета подхватятся сразу.
4. **Продажи** — режим работы и ссылка на менеджера.
5. **Товары** — добавьте первый товар: фото, название, цена.

Не забывайте нажимать «Сохранить настройки» внизу после правок.

**Финальная проверка:** откройте магазин в Telegram, добавьте товар в корзину,
оформите заказ. Вам должно прийти уведомление со списком товаров и контактами
покупателя. Пришло — магазин полностью рабочий.

### Если что-то пошло не так

**«Certbot не смог выпустить сертификат»** — домен ещё не доехал. Проверьте
`ping -c 3 ваш-домен`, дождитесь своего IP и повторите вручную:
`certbot --nginx -d ваш-домен`

**Витрина не открывается** — посмотрите, жив ли сервис: `systemctl status tg-shop`.
Если `failed`, причина будет в `journalctl -u tg-shop -n 50`.

**Уведомления не приходят** — три причины по частоте: не написали боту `/start`;
вписали не тот ID (проверьте `/id`); не нажали «Сохранить настройки».

**Бот не отвечает** — `journalctl -u tg-shop -n 30`. Строка «не удалось
авторизоваться» означает неверный токен в `/opt/tg-shop/.env`.

**«Нет связи с api.telegram.org»** — сервер физически не достаёт Telegram, так
бывает у части российских хостеров. Проверьте: `curl -sS -m 10 https://api.telegram.org | head -c 200`.
Висит или таймаут — либо меняйте хостинг на зарубежный, либо поднимите прокси и
укажите его в `.env`: `TELEGRAM_API_BASE=https://ваш-прокси`.

Точную причину всегда показывает админка: вкладка **Обзор** → «Диагностика».

**Забыли пароль админки** — `grep ADMIN_TOKEN /opt/tg-shop/.env`

## Несколько ботов на одном VPS

Каждый бот — отдельный магазин: своя папка `/opt/shops/<имя>`, свой токен,
домен, порт и свой systemd-сервис `tg-shop@<имя>`. Они изолированы: падение
или обновление одного не трогает соседей.

1. **Первый бот** — `bash install.sh` (как описано выше).
2. **Каждый следующий** — `bash add-shop.sh`: скрипт спросит имя латиницей,
   токен СВОЕГО бота, домен и пароль админки; порт подберёт сам, nginx
   и сертификат настроит. Повторить для каждого бота.
3. **Обновление всех разом и параллельно** — `bash update-all.sh` (по умолчанию
   4 потока, `-j 6` или `UPDATE_JOBS=6` — больше; список ботов — `bots.conf`,
   логи — `/var/log/tg-shop-update/<имя>.log`). Падение одного бота
   не останавливает остальные; в конце — сводка и предупреждения по темам.
4. **Управление**: `systemctl restart tg-shop@<имя>` — один бот,
   `systemctl list-units 'tg-shop@*'` — все.

Лимиты: экземпляр ест ~45–50 МБ RAM — на 1 ГБ VPS комфортно 8–10 ботов,
на 10–15 нужно ~2 ГБ. Лимиты Telegram Bot API считаются на бота, а не
на сервер, поэтому разные токены друг другу не мешают. Подробности —
в разделах «Обновление всех магазинов разом» и «Лимиты VPS при 10–15 ботах».

## Режимы продаж

Переключаются одним селектом на вкладке **Продажи** — это главный тумблер, который
превращает один и тот же код в разные продукты.

| Режим | Что видит покупатель | Кому подходит |
|---|---|---|
| **Корзина + оформление** | Корзина, форма заказа, заказ падает менеджеру в Telegram | Обычный магазин |
| **Только через менеджера** | Корзины нет вообще, кнопка ведёт в личку продавца с готовым текстом | Услуги, штучный товар, торг |
| **Заявка по товару** | Корзины нет, но есть форма — клиент оставляет контакты по одному товару | Заявки, предзаказы, аренда |
| **Витрина без покупки** | Только каталог, кнопок покупки нет | Портфолио, шоурум, меню |

## Что настраивается без кода

**Бренд:** название, эмодзи, логотип, подзаголовок, стиль шапки, описание в профиле,
произвольные ссылки в профиле (соцсети, Avito, канал, сайт).

**Тема:** 12 пресетов оформления (Liquid Glass — по умолчанию, Бруталист, Конструктивизм, Баухаус, Неон,
Швейцарский, Моно, Мягкий, Кислота, ERD, Маркет, Вояж), 7 цветов по отдельности, шрифт, масштаб текста,
скругления, толщина рамок, капслок, плотность вёрстки, число колонок, стиль карточек
(рамка / без рамки / жёсткая тень / наклейки с наклоном), пропорции фото, косые срезы,
зерно плёнки, бегущая строка, режим анимаций, произвольный CSS.

**Каталог:** показывать ли поиск, категории, сортировку и счётчик; сортировка по
умолчанию; показ остатков и порог «осталось мало»; прятать ли раскупленное; бейдж
хитов и его текст; текст пустого каталога.

**Продажи:** режим, тексты кнопок, символ валюты и его позиция, скрытие цен с заменой
на «цена по запросу», минимальная сумма заказа, включение корзины и избранного,
ссылка на менеджера и поддержку, шаблоны сообщений с подстановками.

**Форма заказа:** какие поля спрашивать (имя, телефон + обязательность, email,
комментарий, адрес), списки способов оплаты и доставки, галочка согласия с
собственным текстом, заголовок и текст финального экрана. Ссылка на профиль
покупателя не спрашивается — бот сам прикладывает @username к уведомлению.

**Флоу оформления заказа.** Один экран с четырьмя группами полей — пустые группы
не показываются:

1. **Контакты** — имя (предзаполнено из Telegram), телефон, email; обязательные
поля помечены `*`, валидация подсвечивает конкретное поле с текстом ошибки.
2. **Доставка** — способ выбирается карточками-переключателями, ниже адрес.
3. **Оплата** — такие же карточки-переключатели.
4. **Детали** — комментарий, промокод, галочка согласия; внизу итоговая сумма.

После «Подтвердить заказ» покупатель попадает на экран успеха: анимированная
галочка, номер заказа, состав и сумма, текст «менеджер свяжется» и кнопки
(онлайн-оплата, «Написать менеджеру», возврат в магазин). Служебная карточка
заказа покупателю не показывается — она уходит только менеджеру.

**Уведомления:** несколько получателей, отдельные тумблеры на заказ / на обращение к
менеджеру / на нового пользователя бота, ссылка на профиль клиента, беззвучный режим.

**Бот:** приветствие, текст кнопки, ответ на `/help`, подтверждение заказа
покупателю в чат (шаблон с `{name}`, `{id}` — номер заказа и `{total}` — сумма;
служебная выгрузка заказа покупателю не показывается — только менеджеру).

**Канал:** канал для публикации, ссылка мини-аппа, шаблон поста с переменными, текст
кнопки в посте.

**Оплата:** приём онлайн-платежей через [Platega](https://platega.io) (карты, СБП,
крипта; регистрация без ИП и ООО) либо через произвольную платёжную ссылку с
подстановкой суммы. Заказ помечается оплаченным автоматически по колбэку мерчанта,
менеджеру и покупателю уходят уведомления. Провайдеры подключаются как плагины —
чтобы добавить нового, достаточно дописать объект в `server/payments.js`.

**Бренд и меню:** эмодзи, 9 готовых одноцветных знаков или свой логотип;
подсказка на аватарке, что это меню (стрелка / точка / подпись «Меню» / ничего);
favicon генерируется автоматически из знака и цветов темы.

**Прочее:** режим обслуживания с текстом-заглушкой, локаль, часовой пояс,
экспорт/импорт всей конфигурации в JSON, самодиагностика.

Переменные в шаблонах: `{product}`, `{price}`, `{items}`, `{total}`, `{shop}`,
`{name}`, `{order}`, `{description}`, `{category}`.

## Эксплуатация

```bash
systemctl status tg-shop      # состояние
systemctl restart tg-shop     # перезапуск
journalctl -u tg-shop -f      # живые логи
```

Бэкап и восстановление

Встроенный автобэкап: в админке вкладка «Бэкапы» — тумблер «снимать
автоматически», интервал (6 ч — неделя), сколько копий хранить, кнопки
«Сделать снимок сейчас», «Скачать» (.tar.gz) и «Восстановить». Снимок —
это вся папка данных (настройки, товары, заказы, картинки) с манифестом
sha256: перед восстановлением каждая копия сверяется по контрольным суммам.
Копии лежат в `backups/` рядом с папкой данных; путь меняется через
`BACKUP_DIR` в `.env`. Конфиг бэкапов хранится отдельно и восстановление
не откатывается.

Ручной бэкап через tar, как было:

```bash
tar czf backup.tgz -C /opt/tg-shop data
tar xzf backup.tgz -C /opt/tg-shop && systemctl restart tg-shop
```

Обновление кода на уже работающем сервере:

```bash
cd /root/tg-shop && bash update.sh
```

`update.sh` сам делает `git pull`, раскладывает файлы, перезапускает сервис и
проверяет, что он поднялся и видит Telegram. Перед обновлением снимает бэкап
`data/` в `/root/`. Ничего не спрашивает и не трогает ни `.env`, ни товары.

`install.sh` нужен только для первой установки или когда меняются домен, порт или
токен бота. При повторном запуске он подставит прежние значения из `.env` как
ответы по умолчанию, но всё равно задаст все вопросы и полезет перевыпускать
сертификат — для обычного обновления это лишнее.

### Обновление всех магазинов разом — `update-all.sh`

Когда на одном VPS живёт несколько магазинов (добавляются через `add-shop.sh`),
`update-all.sh` обновляет их все за один прогон — **параллельно**, а не по очереди:

```bash
bash update-all.sh                  # все магазины, 4 параллельных потока
bash update-all.sh -j 6             # 6 потоков (потолок 8)
UPDATE_JOBS=6 bash update-all.sh    # то же через переменную окружения
bash update-all.sh vinty merch      # только перечисленные магазины
UPDATE_BRANCH=main bash update-all.sh   # тянуть код из конкретной ветки
```

Как это устроено:

- **Список магазинов** берётся из `bots.conf` рядом со скриптом (одно имя на
  строку, `#` — комментарий; см. `bots.conf.example`). Если `bots.conf` нет —
  обновляются все магазины из `/opt/shops`, у которых есть `.env`.
- **Код общий**: один `git pull` и один `rsync` в `/opt/tg-shop-code` на всех,
  дальше каждый магазин просто перезапускается — данные и `.env` не трогаются.
- **Параллельность**: рестарт каждого магазина — независимая фоновая задача;
  одновременно выполняется не больше `-j`/`UPDATE_JOBS` задач (по умолчанию 4),
  чтобы не упереться в CPU/IO даже при 10–15 ботах.
- **Логи не смешиваются**: вывод по каждому магазину пишется в
  `/var/log/tg-shop-update/<имя>.log`, в stdout — по одной строке результата.
- **Отказоустойчивость**: если один магазин не поднялся (конфликт, кривой
  `.env` и т.п.), остальные всё равно обновляются; в конце скрипт печатает
  сводку (кто обновился, кто упал, хвосты логов) и выходит с кодом 1.
- **Ветка git** не захардкожена: текущая ветка репозитория, либо `branch=<имя>`
  в `bots.conf`, либо `UPDATE_BRANCH`. Если ветка существует только локально и
  её нет в `origin` (так было с `pr-1`), скрипт не падает на `git pull`,
  а пропускает pull и раскатывает локальный код.
- Перед рестартом каждого магазина снимается бэкап его `data/` в `/root/`.

### Лимиты VPS при 10–15 ботах

Каждый магазин — отдельный процесс Node.js (`tg-shop@<имя>`, свой systemd-unit),
поэтому падение одного не роняет остальные; общего процесса на все боты нет.
Перед раскаткой на 10–15 ботов проверьте:

- **RAM** — главный ограничитель: экземпляр ест ~45–50 МБ. 10–15 ботов —
  это ~1,5–2 ГБ только под них, плюс nginx и система. На гигабайтном VPS
  комфортно живут 8–10 магазинов; `update-all.sh` сам прикидывает RAM
  и предупреждает, если её впритык.
- **CPU** — нагрузка в простое минимальна (long polling), пики только в момент
  рестартов; чтобы они не конкурировали, `update-all.sh` и держит потолок
  параллельных потоков (`-j`, по умолчанию 4).
- **Открытые файлы** — на каждый процесс Node нужны десятки fd; дефолтного
  `ulimit -n 1024` на 15 ботов хватает, но если хостер его занизил —
  поднять (`ulimit -n 65536` / `LimitNOFILE` в unit-файле).
- **Telegram Bot API** — лимиты считаются **на бота** (~30 сообщений/сек),
  а не на сервер, поэтому 15 разных токенов друг другу не мешают. Единственная
  общая точка — исходящий IP: если ботов очень много и все одновременно
  шлют уведомления, возможна общая очередь `429`, но магазин с его объёмами
  в неё не упирается. Параллельный рестарт безопасен: на один токен никогда
  не работают два poller-процесса (systemctl сначала останавливает старый).

### Клонирование магазина под другого клиента

Админка → **Ещё** → «Экспорт» сохранит настройки и товары в JSON. На новом сервере
после установки — «Импорт». Фотографии при этом не переносятся (они лежат в
`data/images`), их можно скопировать отдельно: `rsync -a data/images/ new-server:/opt/tg-shop/data/images/`.

## MySQL-схема и миграции (этап SaaS)

Пока `MYSQL_HOST` не задан, магазин живёт на файлах, как раньше: БД
в этом этапе нужна только самой схеме. Подключение настраивается
переменными `MYSQL_*` (см. `.env.example`), дальше:

```bash
node server/migrate.js up       # применить все ожидающие миграции
node server/migrate.js status   # что применено, что ожидает
```

Миграции — файлы `server/migrations/*.sql`, применяются по алфавиту имён.
Каждая фиксируется в `schema_migrations` вместе с sha256 файла, поэтому:

- повторный прогон безопасен (идемпотентность);
- правка уже применённого файла отклоняется — изменения только новой
  миграцией (`0002_...`).

Схема `0001_core` закладывает основу мультитенантности: `tenants →
shops → данные магазина`. Все таблицы магазина несут `shop_id` и
каскадно удаляются вместе с магазином; настройки и заказы хранят
JSON-колонки, а заказ дополнительно держит `raw` — исходный объект
целиком, чтобы будущий перенос из `orders.json` прошёл без потерь.

Единственная добавленная зависимость — драйвер `mysql2`: протокол MySQL
с нуля не пишут, а в файловом режиме он даже не загружается.

Тесты миграций (`test/migrations.test.js`) ходят в живую БД и сами
пропускаются, если MySQL недоступен.

## Установка платформы — пошагово

Это второй сценарий: не один магазин, а сервис, где клиенты регистрируются сами
и каждый получает свой поддомен. Ставится поверх того же сервера; если вы уже
прошли гайд выше, шаги 1–3 пропускайте.

Отличий от одиночной установки три: нужна база MySQL, нужен домен **с
поддоменами**, и сертификат нужен **wildcard** — один на все магазины сразу.

### Шаг 1. Домен для платформы

Годятся оба варианта из гайда выше, но с оговорками.

**DuckDNS работает и здесь** — проверено: `клиент.мойшоп.duckdns.org` резолвится
на тот же IP, что и `мойшоп.duckdns.org`, без всякой настройки. Магазины клиентов
будут выглядеть как `pizza.мойшоп.duckdns.org`.

**Свой домен лучше** — не потому что технически, а потому что клиенту вы
продаёте адрес. `pizza.вашсервис.ру` против `pizza.мойшоп.duckdns.org` — разница
в доверии заметная. Если берёте свой домен, добавьте в DNS **две A-записи**:
`@` и `*`, обе на IP сервера.

### Шаг 2. Поставить MySQL

```bash
apt update && apt install -y mariadb-server
```

> Важно: проекту нужен именно **MySQL 8.0.19+**, а не MariaDB — используется
> синтаксис `INSERT ... AS new ON DUPLICATE KEY UPDATE`, которого в MariaDB нет.
> На Debian 12 ставьте MySQL из репозитория Oracle:
> ```bash
> wget https://dev.mysql.com/get/mysql-apt-config_0.8.34-1_all.deb
> dpkg -i mysql-apt-config_0.8.34-1_all.deb && apt update && apt install -y mysql-server
> ```

Создайте базу и пользователя (пароль придумайте свой, длинный):

```bash
mysql -u root -p -e "CREATE DATABASE shops CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci; CREATE USER 'shops'@'127.0.0.1' IDENTIFIED BY 'ПРИДУМАЙТЕ_ПАРОЛЬ'; GRANT ALL ON shops.* TO 'shops'@'127.0.0.1'; FLUSH PRIVILEGES;"
```

### Шаг 3. Wildcard-сертификат

Обычный сертификат выпускается проверкой по HTTP и покрывает один адрес.
Wildcard (`*.вашдомен`) так выпустить нельзя — Let's Encrypt требует доказать
владение доменом через DNS, добавив TXT-запись.

**Для своего домена** проще всего перевести DNS на Cloudflare (бесплатно) и
поставить плагин:

```bash
apt install -y python3-certbot-dns-cloudflare
certbot certonly --dns-cloudflare --dns-cloudflare-credentials /root/cf.ini -d 'вашдомен.ру' -d '*.вашдомен.ру'
```

**Для DuckDNS** есть отдельный плагин:

```bash
apt install -y python3-pip && pip3 install certbot-dns-duckdns --break-system-packages
certbot certonly --authenticator dns-duckdns --dns-duckdns-token ВАШ_ТОКЕН_DUCKDNS -d '*.мойшоп.duckdns.org'
certbot certonly --authenticator dns-duckdns --dns-duckdns-token ВАШ_ТОКЕН_DUCKDNS -d 'мойшоп.duckdns.org'
```

> **Ловушка DuckDNS: нужны два сертификата, а не один.** DuckDNS хранит только
> одну TXT-запись на домен, а совмещённый запрос (`-d домен -d *.домен`)
> требует двух разных TXT одновременно. Поэтому выпускайте отдельно wildcard и
> отдельно сам домен — командами выше, именно в таком порядке. Попытка
> сделать одной командой падает с невнятной ошибкой проверки.

### Шаг 4. Настроить и запустить

В `.env` платформы:

```
MULTITENANT=1
MULTITENANT_DOMAIN=мойшоп.duckdns.org
SECRET_KEY=длинная-случайная-строка-минимум-12-символов
MYSQL_HOST=127.0.0.1
MYSQL_USER=shops
MYSQL_PASSWORD=пароль-из-шага-2
MYSQL_DATABASE=shops
PLATFORM_OFFER_URL=https://мойшоп.duckdns.org/offer.html
PLATFORM_PRIVACY_URL=https://мойшоп.duckdns.org/privacy.html
```

> `SECRET_KEY` шифрует токены ботов ваших клиентов. **Потеряете его — все боты
> перестанут подниматься** (магазины продолжат работать, это предусмотрено).
> Храните отдельно от бэкапа базы: вместе они дают доступ ко всем ботам разом.

> `PLATFORM_OFFER_URL` и `PLATFORM_PRIVACY_URL` — ссылки на вашу оферту и
> политику обработки данных. Форма регистрации требует согласия с ними, и это
> не формальность: вы собираете почту и создаёте аккаунты. Документы должны
> существовать до первого клиента.

Накатите схему и запустите:

```bash
node server/migrate.js up && systemctl restart tg-shop
```

В логе появится `[platform] http://…  (домен: …, магазинов: 0, биллинг: выключен)`.
Откройте `https://мойшоп.duckdns.org/` — увидите лендинг с формой регистрации.

### Шаг 5. Проверить

Зарегистрируйте пробный магазин прямо на лендинге. Должно получиться:
магазин открывается на своём поддомене, пароль админки показан один раз (есть
кнопка «Скопировать»), в админке на вкладке «Бот» можно вставить токен от
BotFather — и бот подключится без перезапуска сервера.

## Режим платформы (мультитенантность)

`MULTITENANT=1` переводит процесс из «один магазин» в «платформа»:

- реестр арендаторов живёт в MySQL (`tenants → shops`), миграции при
  старте накатываются сами;
- каждый магазин отвечает на своём поддомене: `shop1.example.ru`,
  голый домен `example.ru` отдаёт лендинг с регистрацией;
- регистрация `POST /api/platform/register` создаёт магазин «под ключ»:
  строки реестра, документы в `shop_docs`, папку для картинок в
  `MULTITENANT_DATA_ROOT`, одноразовый пароль админки (в БД уходит
  только sha256) и, опционально, бота — токен шифруется AES-256-GCM на
  ключе `SECRET_KEY` и в открытом виде нигде не хранится;
- данные магазина живут в MySQL (`store-db.js`, таблица `shop_docs`): тот же
  интерфейс, что у файлового `store.js` — чтение синхронное из кэша, запись
  очередью UPSERT. Магазин переживает рестарт и перенос процесса; на диске
  остаются только картинки. Бэкапы папки в этом режиме отключены —
  источник правды БД, её копии ведёт инфраструктура (dump/репликация);
- обработчики API не знают о мультитенантности: запрос через
  `AsyncLocalStorage` получает «своего» арендатора, а короткие имена
  (`store`, `ordersRepo`, `bot`, `tgApi`…) резолвятся в него на лету.

Требуемые переменные: `MYSQL_HOST/MYSQL_DATABASE`, `MULTITENANT_DOMAIN`,
`SECRET_KEY` (от 12 символов); необязательные — `MULTITENANT_DATA_ROOT`
(по умолчанию `./data/shops`). Без `MULTITENANT=1` всё работает в прежнем
файловом режиме одного магазина — переключатель, а не переезд.

Перенос существующего файлового магазина на платформу — одна команда:

```bash
node server/import-shop.js /путь/к/data myshop
```

Импортёр раскладывает данные в два слоя без потерь: живые документы
магазина — в `shop_docs` (витрина платформы читает их через `store-db`),
картинки — в папку магазина; плюс структурированная копия в MySQL
(`legacy_id` связывает старые id с новыми, заказы и товары дополнительно
лежат в `raw`-колонках целиком). На выходе — одноразовый пароль админки.

Сквозной тест (`test/multitenant.test.js`) поднимает настоящую платформу
на случайном порту и проверяет регистрацию, изоляцию настроек двух
магазинов, гейт пароля админки, 404 на неизвестном поддомене и главное —
что магазины переживают рестарт платформы, потому что данные в БД.
`test/store-db.test.js` проверяет само хранилище: синхронный кэш, очередь
записи, изоляцию по `shop_id` и картинки на диске.

## Подписка магазинов (биллинг, опционально)

Плата продавца за работу магазина на платформе — через Robokassa
(`server/billing.js` + `server/robokassa.js`). **Биллинг полностью
опционален**: без `ROBOKASSA_LOGIN` и паролей магазины работают бесплатно
и бессрочно. **Приём денег от покупателей это не затрагивает**: онлайн-оплата
заказов живёт в `payments.js` и настройках каждого магазина (вкладка
«Оплата») и от подписки не зависит.

Как это устроено:

- новый магазин получает пробный период (`BILLING_TRIAL_DAYS`, по умолчанию
  14 дней от регистрации);
- продавец в админке (вкладка «Подписка») нажимает «Оплатить» — выставляется
  счёт и открывается касса Robokassa;
- Result-уведомление на `https://<домен>/api/platform/billing/result`
  проверяет подпись (Password2) и сумму, продлевает подписку на
  `BILLING_PERIOD_DAYS` (оплата впрок добавляется к хвосту текущей, а не
  сгорает) и снимает приостановку;
- просрочка переводит магазин в `suspended`: витрина отдаёт 402 со
  страницей-объяснением, а админка и оплата продолжают работать, чтобы
  продавец мог продлить; бот приостановленного магазина останавливается.

Переменные (все необязательные): `ROBOKASSA_LOGIN`, `ROBOKASSA_PASS1`,
`ROBOKASSA_PASS2`, `ROBOKASSA_IS_TEST`, `BILLING_PRICE` (по умолчанию 990 ₽),
`BILLING_PERIOD_DAYS` (30), `BILLING_TRIAL_DAYS` (14). В кабинете Robokassa:
Result Url = `https://<MULTITENANT_DOMAIN>/api/platform/billing/result`,
метод POST. Тесты: `test/billing.test.js` — подписи, счета, пробный период,
приостановка и полный цикл оплаты через HTTP с рестартом платформы.

## Как поднять несколько ботов на одном сервере

В файловом режиме бот один (`BOT_TOKEN`). Несколько ботов — это режим
платформы: один процесс Node обслуживает N магазинов, у каждого свой бот,
свой поддомен, свои данные в MySQL.

1. **Домен.** Нужен домен и wildcard-запись в DNS: `*.example.ru` → IP
   сервера (плюс запись для голого `example.ru` — это лендинг платформы).
2. **HTTPS.** Wildcard-сертификат на `*.example.ru` (Let's Encrypt умеет).
3. **Прокси.** nginx проксирует все поддомены в один порт Node:

   ```nginx
   server {
     listen 443 ssl;
     server_name example.ru *.example.ru;
     # ... ssl_certificate ...
     location / {
       proxy_pass http://127.0.0.1:3000;
       proxy_set_header Host $host;
       proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
     }
   }
   ```

   Платформа сама разберёт `Host`: голый домен — лендинг, `shop1.example.ru` —
   магазин `shop1`.
4. **`.env`**: `MULTITENANT=1`, `MULTITENANT_DOMAIN=example.ru`, MySQL
   (`MYSQL_HOST`, `MYSQL_DATABASE`…), `SECRET_KEY` (от 12 символов).
   Биллинг — по желанию (`ROBOKASSA_*`, см. раздел выше).
5. **Запуск**: `node server/index.js` — миграции накатятся сами.
6. **Боты.** У каждого магазина — свой токен от @BotFather, два способа:
   - форма регистрации на лендинге: поле «Токен бота» (можно оставить
     пустым и добавить позже);
   - переезд существующего магазина со своим ботом: импортёр берёт токен
     из `BOT_TOKEN` в `.env`:
     `BOT_TOKEN=123456:AA… node server/import-shop.js /путь/к/data myshop`

   Токены хранятся в БД зашифрованными (AES-256-GCM на `SECRET_KEY`).
   По умолчанию боты работают на long polling — ничего настраивать не надо;
   `BOT_MODE=webhook` включает вебхуки сразу для всех магазинов платформы.

Дальше магазины живут сами: регистрация с лендинга, данные в MySQL,
приостановка просроченных подписок (если включён биллинг).

## Магазин как объект, а не как процесс

`server/tenant.js` собирает магазин целиком: папку данных, хранилище, заказы,
токен бота, пароль админки, публичный адрес. Всё остальное — `store`, `orders`,
`telegram`, `bot` — это фабрики, а не синглтоны, и состояние живёт в экземпляре.

Практический смысл: один процесс Node может обслуживать сколько угодно
магазинов, ничего между ними не смешивая. Раньше это было невозможно —
папка данных, токен бота и курсор опроса лежали на уровне модулей, поэтому
«процесс» и «магазин» были одним и тем же понятием, и каждый новый магазин
требовал отдельного systemd-юнита, порта и папки.

Сегодня объект по-прежнему создаётся ровно один в обычном режиме и
собирается из тех же переменных окружения. В режиме платформы
(`MULTITENANT=1`) объекты создаются на каждый магазин из реестра MySQL,
а запрос выбирает своего арендатора по поддомену — см. раздел «Режим
платформы».

Проверяется тестом `test/tenant.test.js`: два магазина в одном процессе, у
каждого свои товары, настройки, заказы, картинки, пароль и секрет вебхука.

## Long polling или webhook

По умолчанию бот работает на **long polling** — и для одного сервера это осознанный
выбор, а не упрощение.

Частое заблуждение: «polling медленный». Медленный — *короткий* polling, когда бот
дёргает сервер по таймеру. Наш вызывает `getUpdates` с `timeout=30`, то есть держит
соединение открытым, и Telegram отдаёт сообщение в тот же момент, когда оно пришло.
Разница в задержке с вебхуком — единицы миллисекунд.

Второе, что стоит учитывать: **уведомления о заказах — это исходящие `sendMessage`,
и транспорт на них не влияет вообще**. Скорость «отстука» менеджеру одинакова
в обоих режимах.

| | long polling | webhook |
|---|---|---|
| Работает до выпуска сертификата | да | нет |
| Переживает падение nginx / протухший сертификат | да, переподключится | нет, апдейты теряются |
| Несколько экземпляров за балансировщиком | нет, `409 Conflict` | да |
| Потолок пропускной способности | 100 апдейтов за запрос, последовательно | до 100 параллельных соединений |
| Нужен публичный HTTPS на 443/80/88/8443 | нет | да |

Вебхук объективно выигрывает в одном: горизонтальное масштабирование. Telegram
запрещает параллельные `getUpdates` под одним токеном, поэтому раскинуть бота на
несколько подов можно только вебхуком. Именно поэтому на нём сидят крупные боты —
но у магазина на одном VPS этой задачи нет.

### Как включить вебхук

Если всё же нужен — он реализован, включается одной строкой в `.env`:

```
BOT_MODE=webhook
```

и `systemctl restart tg-shop`. Требования: `PUBLIC_URL` начинается с `https://`
и сертификат валиден. Бот сам вызовет `setWebhook` на `PUBLIC_URL/api/webhook`.

Отдельный секрет заводить не нужно: он выводится из `BOT_TOKEN` + `ADMIN_TOKEN`,
передаётся Telegram в заголовке `X-Telegram-Bot-Api-Secret-Token` и сверяется на
каждом запросе — без этого адрес был бы открытым приёмником поддельных сообщений.

Если `setWebhook` не прошёл (нет HTTPS, сертификат протух, домен не резолвится) —
бот **не падает, а автоматически откатывается на long polling** и пишет причину
в лог. Обратно переключиться: убрать строку из `.env` и перезапустить, вебхук
снимется сам.

## Same-Origin Restriction

С 2026 года Telegram включает это ограничение всем мини-аппам автоматически:
методы WebApp SDK разрешено вызывать только со своего домена. В @BotFather оно
видно как переключатель **Same-Origin Restriction**.

**Этот магазин ограничению соответствует, оставляйте его включённым.** Витрина
целиком лежит на одном домене, единственный скрипт со стороны —
`telegram-web-app.js` с telegram.org, а он исполняется в контексте нашей
страницы и под ограничение не подпадает. Ни одного `iframe` с чужого домена в
витрине нет: превью в админке грузится со своего же адреса.

Внешние ссылки (менеджер, оплата, соцсети) открываются через `openLink` /
`openTelegramLink` как отдельные страницы и SDK не трогают — на них ограничение
тоже не влияет.

Отключать его смысла нет: opt-out перекладывает на вас ответственность за то,
что мини-апп не ведёт на недоверенные сайты.

## Совместимость с версиями Telegram

Витрина рассчитана на старые клиенты: всё, что появилось позже базовой версии,
вызывается только после проверки `isVersionAtLeast`, а при отсутствии поддержки
функция просто не включается — экран не ломается.

| Возможность | Нужен Bot API | Если клиент старее |
|---|---|---|
| `disableVerticalSwipes` — свайп по галерее не сворачивает мини-апп | 7.7 | свайп вниз может свернуть приложение |
| `safeAreaInset` / `contentSafeAreaInset` | 8.0 | отступы берутся из CSS `env(safe-area-inset-*)` |
| Произвольный hex в `setHeaderColor` | 6.9 | шапка красится ключевым словом `bg_color` |
| `BackButton`, `HapticFeedback`, `setBackgroundColor` | 6.1 | шторки закрываются крестиком, вибрации нет |
| `MainButton`, `viewportStableHeight` | базовые | — |

Про горизонтальные свайпы отдельно: на iOS свайп от самого края экрана — это
системный жест «назад», и карусель у края экрана может его поймать. Поэтому
галерея не прижата к краю (у шторки есть внутренний отступ), а под ней всегда
показаны точки и счётчик кадров — это подсказывает, что элемент листается, и
пользователь начинает жест не от кромки. Полностью отключить системный жест из
веба нельзя ни одним SDK.

## Тема: единственный источник правды и почему витрина может стать светлой

Полный аудит всех мест, откуда берётся тема:

| Источник | Что делает | Может сделать витрину светлой? |
|---|---|---|
| `data/settings.json` → `theme` | **Единственный источник правды** — сохранённые настройки магазина | Только если продавец сам сохранил светлый пресет (`Маркет`, `Швейцарский`, `Баухаус`, `Конструктивизм`) или ручные светлые цвета |
| `server/index.js` → `bootThemeCSS` | Вписывает палитру из настроек в первый кадр HTML | Нет: берёт только из настроек |
| `public/theme-core.js` | Пресеты и `resolveTheme` | Нет: светлые пресеты применяются только при явном выборе |
| `public/shared.js` → `applyTheme` | Раскладывает настройки в CSS-переменные | Нет |
| `public/index.html` → `telegramThemeMix`, boot-перекрытие, `themeChanged` | **Только при `theme.colorScheme='telegram'`** подмешивает `themeParams` покупателя | **Да — единственное автоматическое наследование.** У покупателя со светлой темой Telegram витрина и кнопки станут белыми, что бы ни сохранил продавец |
| `localStorage shop_theme_v2` | Первый кадр до ответа `/api/settings` | Нет: это копия последних применённых настроек; при падении загрузки остаётся она же |
| `:root` в `index.html` / `admin.html` | Дефолт до загрузки настроек | Нет: всегда тёмный (`#0d0d0d`) |
| `Telegram.WebApp.colorScheme` | Синхронизируется только в CSS `color-scheme` для нативных контролов | Нет: цвета палитры не трогает |
| `prefers-color-scheme` / service worker / CDN | — | В проекте отсутствуют |

Дополнительно закрытые лазейки: не-hex цвета продавца (rgb(), названия) раньше
оставляли `setHeaderColor`/`setBackgroundColor` без значения, и шапка/фон
доставались от темы клиента — теперь любой CSS-цвет разрешается в hex; отсутствующие
ключи `themeParams` больше не пишут `undefined` в переменные.

**Если дизайн задуман строго тёмным** (хардкод, независимо от темы Telegram и
системы пользователя): в админке магазина должно быть сохранено
`theme.colorScheme = «Своя тёмная»` и тёмный пресет. Режим «Подстроиться под
тему Telegram» — осознанная фича, а не баг: он намеренно отдаёт палитру
покупателю, и админка показывает об этом предупреждение.

Важно про асимметрию: **админка и превью никогда не применяют `themeParams`**
(браузер вне Telegram их просто не имеет) — продавец всегда видит свою палитру,
даже когда у покупателей витрина белая. Поэтому тема проверяется только на
реальном клиенте Telegram, а не по превью.

### Регресс-чеклист темы при каждом деплое

1. `update-all.sh` после рестарта печатает сохранённую тему каждого магазина
   (`preset=… scheme=…`) и сам предупреждает про `scheme=telegram` и светлые
   пресеты — читать его вывод.
2. Открыть витрину в Telegram с **тёмной** темой: фон и кнопки совпадают
   с тем, что в админке.
3. Открыть ту же витрину в Telegram со **светлой** темой: фон остаётся тёмным
   (если `scheme=dark`); при `scheme=telegram` витрина обязана посветлеть.
4. Повторить п. 2–3 в десктоп-клиенте Telegram — код один, но проверять нужно
   оба: рендер WebView отличается.
5. После смены оформления в админке — открыть витрину инкогнито/с другого
   устройства: сервер шлёт `no-cache` + ETag с отпечатком настроек, но
   агрессивный прокси между VPS и клиентом может держать старый HTML.

## Заказы

Вкладка **Заказы** в админке: фильтр по статусу со счётчиками, смена статуса
прямо в карточке, выгрузка в CSV и постраничная подгрузка.

Статусы линейные: новый → в работе → отправлен → выполнен, плюс отдельный
«отменён». Отменённые заказы не попадают в сумму продаж на «Обзоре» — иначе
цифра в админке расходится с деньгами на счёте.

История хранится **целиком**. Последние 500 заказов лежат в `data/orders.json`,
всё, что старше, — в `data/orders-archive.json`. Фильтр, поиск статуса и
выгрузка видят оба файла; админка подгружает список страницами, поэтому
архив на десятки тысяч записей не замедляет открытие вкладки.

Выгрузка CSV открывается в Excel как есть: разделитель `;`, BOM в начале
(без него Excel читает UTF-8 как cp1251 и показывает кракозябры), дробные
числа с запятой в русской локали. Один заказ — одна строка, включая
контакты, состав, промокод и итог.

## Тесты

```bash
npm test
```

Без зависимостей — встроенный `node:test`. Покрыты места, где ошибка
дорого стоит: архивация заказов (ни один не должен потеряться), смена
статусов, экранирование CSV, тормоз на подбор пароля. Плюс сквозной тест,
который поднимает настоящий сервер на временной папке данных и проходит
путь «заказ → админка → статус → выгрузка».

## Безопасность

- Админка защищена одним токеном из `.env`, сравнение — константное по времени.
- Подбор пароля упирается в растущую паузу: после нескольких неудач с одного
  адреса вход блокируется на 30 секунд, дальше время удваивается до 15 минут.
  Удачный вход счётчик обнуляет.
- Заказы принимаются с проверкой подписи `initData`; заказ без валидной подписи
  помечается в уведомлении как неподтверждённый.
- Цены и названия для заказа берутся из базы, а не из того, что прислал клиент.
- Остатки, скрытые товары, режим обслуживания и обязательные поля формы
  проверяются на сервере, а не только на витрине.
- Факт оплаты витрина узнаёт у сервера по одноразовому ключу, а не из адресной
  строки: возврат от мерчанта сам по себе ничего не подтверждает.
- На публичные ручки стоит rate limit по IP.
- Сервис работает под непривилегированным пользователем, systemd даёт ему доступ
  на запись только в `data/`.

Что стоит сделать дополнительно: закрыть SSH по паролю, поднять ufw, и не давать
пароль от админки лишним людям — прав внутри неё нет, она полностью админская.

## Прежний деплой на Netlify

Папка `netlify/` осталась от первой версии проекта. **Она не совместима с текущей
схемой настроек** (там старый плоский формат, без режимов продаж и тем) и не
поддерживается. Если разворачиваете на VPS — эту папку и `netlify.toml` можно
просто удалить.
